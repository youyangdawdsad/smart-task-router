# 崩溃风险检测（Crash Detector）

## 概述

崩溃风险检测模块负责在任务分发到电脑端之前，评估该任务是否可能导致电脑端崩溃（内存溢出、CPU 过载、进程卡死等）。当检测到高风险时，自动将任务拆分为更小的子任务，并通过副链路通知手机端，由手机端协调分步执行。

## 核心问题

电脑端在执行以下类型任务时存在崩溃风险：
- 处理超大文件（如几 GB 的视频、大型数据集）
- 运行内存密集型脚本（如深度学习推理）
- 同时打开多个重型应用（如 IDE + 浏览器 + 数据库）
- 执行未经验证的第三方代码
- 批量文件操作（如同时压缩 1000 个文件）

当电脑端崩溃后，当前的 device_chat 主链路会断开，手机端无法主动联系电脑端恢复任务。因此需要**提前预防**而非事后补救。

## 风险评估模型

### 风险因子

| 因子ID | 因子名称 | 权重 | 检测方式 |
|--------|----------|------|----------|
| RF-001 | 文件大小风险 | 0.25 | 任务涉及的文件总大小 |
| RF-002 | 内存占用风险 | 0.25 | 预估内存峰值 |
| RF-003 | CPU 负载风险 | 0.15 | 当前 CPU 使用率 + 预估增量 |
| RF-004 | 并发任务风险 | 0.15 | 当前正在执行的任务数 |
| RF-005 | 代码风险 | 0.10 | 是否执行未知/第三方代码 |
| RF-006 | 磁盘空间风险 | 0.10 | 可用磁盘空间 |

### 风险评分计算

```
risk_score = Σ(factor_score × weight) for all factors
```

每个因子评分 0-1：
- 0.0-0.3：低风险
- 0.3-0.7：中风险
- 0.7-1.0：高风险

### 因子评分规则

#### RF-001: 文件大小风险

| 条件 | 评分 |
|------|------|
| 所有文件 < 100MB | 0.1 |
| 任一文件 100MB-1GB | 0.4 |
| 任一文件 1GB-5GB | 0.7 |
| 任一文件 > 5GB | 0.95 |

#### RF-002: 内存占用风险

| 条件 | 评分 |
|------|------|
| 预估峰值 < 50% 可用内存 | 0.1 |
| 预估峰值 50-70% 可用内存 | 0.4 |
| 预估峰值 70-90% 可用内存 | 0.7 |
| 预估峰值 > 90% 可用内存 | 0.95 |

#### RF-003: CPU 负载风险

| 条件 | 评分 |
|------|------|
| 当前 CPU < 30% | 0.1 |
| 当前 CPU 30-60% | 0.3 |
| 当前 CPU 60-80% | 0.6 |
| 当前 CPU > 80% | 0.9 |

#### RF-004: 并发任务风险

| 条件 | 评分 |
|------|------|
| 当前任务数 = 0 | 0.0 |
| 当前任务数 1-2 | 0.2 |
| 当前任务数 3-4 | 0.5 |
| 当前任务数 ≥ 5 | 0.8 |

#### RF-005: 代码风险

| 条件 | 评分 |
|------|------|
| 不涉及代码执行 | 0.0 |
| 已知安全的代码 | 0.2 |
| 第三方/未知代码 | 0.7 |
| 涉及系统级操作 | 0.9 |

#### RF-006: 磁盘空间风险

| 条件 | 评分 |
|------|------|
| 可用空间 > 10GB | 0.0 |
| 可用空间 5-10GB | 0.3 |
| 可用空间 1-5GB | 0.6 |
| 可用空间 < 1GB | 0.9 |

## 风险处置策略

### 低风险（risk_score < 0.3）

- 正常路由到电脑端
- 指示器输出绿色状态
- 无需特殊处理

### 中风险（0.3 ≤ risk_score < 0.7）

- 正常路由到电脑端
- 指示器输出黄色警告
- 建议用户关注执行状态
- 记录风险日志供后续分析

### 高风险（risk_score ≥ crash_risk_threshold，默认 0.7）

- **拦截任务**，不直接路由到电脑端
- 自动拆分为更小的子任务
- 通过副链路通知手机端
- 手机端协调分步执行

## 任务拆分策略

当高风险拦截触发时，按以下策略拆分：

### 按文件拆分

如果任务涉及多个文件：
```
原始任务：处理 5 个大文件
拆分结果：
  ST-1: 处理文件1（< 1GB）
  ST-2: 处理文件2（< 1GB）
  ...
  ST-5: 处理文件5（< 1GB）
  ST-6: 汇总所有结果
```

### 按步骤拆分

如果任务是多步骤流程：
```
原始任务：读取数据 → 分析 → 生成报告
拆分结果：
  ST-1: 读取数据（限制内存使用）
  ST-2: 分析数据（使用流式处理）
  ST-3: 生成报告
```

### 按资源拆分

如果任务资源密集：
```
原始任务：同时运行3个脚本
拆分结果：
  ST-1: 运行脚本1
  ST-2: 运行脚本2（等待ST-1完成）
  ST-3: 运行脚本3（等待ST-2完成）
```

## 手机端分步通知

### 通知格式

当电脑端检测到高风险并通过副链路通知手机端时，手机端收到的通知格式：

```json
{
  "type": "crash_risk_split",
  "from_device": "pc-01",
  "original_task_id": "T-xxx",
  "risk_score": 0.85,
  "risk_factors": ["large_file_processing", "memory_intensive"],
  "sub_tasks": [
    {"id": "ST-1", "text": "处理文件1", "estimated_memory_mb": 512},
    {"id": "ST-2", "text": "处理文件2", "estimated_memory_mb": 512},
    {"id": "ST-3", "text": "汇总结果", "estimated_memory_mb": 128}
  ],
  "execution_plan": {
    "strategy": "sequential",
    "delay_between_ms": 2000,
    "max_concurrent": 1
  }
}
```

### 手机端处理流程

1. 收到高风险通知
2. 解析子任务列表和执行计划
3. 按执行计划逐步调度：
   - 向电脑端发送 ST-1
   - 等待 ST-1 完成
   - 向电脑端发送 ST-2
   - 等待 ST-2 完成
   - ...
4. 汇总所有子任务结果
5. 向用户报告最终结果

### 手机端保护机制

- 每个子任务设置超时（默认 60 秒）
- 子任务失败时跳过并记录，不阻塞后续子任务
- 所有子任务完成后统一汇报，避免通知轰炸

## 风险日志

```json
{
  "log_id": "CRASH-{timestamp}",
  "task_id": "T-xxx",
  "device": "pc-01",
  "risk_score": 0.85,
  "risk_factors": {
    "RF-001": 0.7,
    "RF-002": 0.9,
    "RF-003": 0.3,
    "RF-004": 0.2,
    "RF-005": 0.0,
    "RF-006": 0.1
  },
  "action": "split_and_notify",
  "sub_task_count": 3,
  "timestamp": "ISO8601"
}
```

## 边界

- 崩溃检测不阻塞紧急任务（urgent 任务降低阈值 0.2）
- 风险评估基于预估值，不保证 100% 准确
- 拆分后的子任务仍可能失败（由 FailoverMigration 处理）
- 风险日志保留最近 200 条

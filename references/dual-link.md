# 双链路通信（Dual Link）

## 概述

双链路通信机制解决的核心问题是：**电脑端和手机端之间的通信可靠性**。

在 v1.x 中，所有通信都依赖 device_chat 主链路。这意味着：
- 电脑端启动后，手机端才能通过 device_chat 与电脑端通信
- 如果主链路断开（网络波动、进程重启），两端完全失联
- 电脑端崩溃后，手机端无法主动感知和恢复

双链路机制在 device_chat 主链路之外，新增一条**网络心跳副链路**，采用**一主一副**架构：
- **主链路（Primary）**：device_chat，用于任务分发和结果回传
- **副链路（Secondary）**：网络心跳，用于保活检测和紧急通知

## 架构设计

```
┌──────────────┐                    ┌──────────────┐
│   电脑端 PC   │◄──── 主链路 ────►│  手机端 Phone  │
│  (SIE 主节点) │◄──── 副链路 ────►│  (SIE 协作节点) │
└──────────────┘                    └──────────────┘
       │                                   │
       │  PC 启动时自动建立                  │
       │  副链路连接                         │
       └───────────────────────────────────┘
```

### 一主一副原则

- **主链路为主**：所有正常任务分发、结果回传都走 device_chat
- **副链路为辅**：仅用于心跳保活、链路状态检测、紧急通知
- **主链路优先**：当主链路可用时，副链路不承担业务流量
- **副链路兜底**：当主链路断开时，副链路用于感知和恢复

## 副链路建立流程

### PC 端启动时自动建立

```
PC 端 Agent 启动
  → 初始化 SIE 引擎
  → 检查 dual_link_enabled 配置
  → 如果启用：
      → 启动网络心跳服务（监听端口：动态分配）
      → 向手机端发送 "link_establish" 握手消息
      → 等待手机端 "link_ack" 响应
      → 收到响应 → 副链路建立成功
      → 超时未收到 → 记录日志，等待重试
  → 开始周期性心跳（默认 15 秒间隔）
```

### 手机端响应流程

```
手机端收到 "link_establish" 消息
  → 验证来源设备 ID
  → 记录 PC 端副链路信息（IP、端口、心跳间隔）
  → 回复 "link_ack"
  → 启动本地心跳响应服务
  → 开始响应 PC 端的心跳请求
```

### 连接建立的时机

| 场景 | 谁发起 | 说明 |
|------|--------|------|
| PC 端首次启动 | PC → 手机 | PC 主动建立副链路 |
| PC 端重启 | PC → 手机 | 重新建立副链路 |
| 手机端先在线 | 等待 PC | 手机端被动等待 PC 发起 |
| 两端同时在线 | PC → 手机 | PC 端优先发起 |

**关键设计**：副链路始终由 PC 端发起建立。这是因为 PC 端作为 SIE 主节点，启动时需要主动注册自己的副链路信息。

## 心跳协议

### 心跳消息格式

```json
{
  "type": "heartbeat",
  "from": "pc-01",
  "to": "phone-01",
  "timestamp": "ISO8601",
  "link": "secondary",
  "payload": {
    "pc_status": {
      "cpu_load": 0.35,
      "memory_usage": 0.62,
      "disk_free_gb": 45.2,
      "current_tasks": 1,
      "uptime_seconds": 3600
    }
  }
}
```

### 心跳响应格式

```json
{
  "type": "heartbeat_ack",
  "from": "phone-01",
  "to": "pc-01",
  "timestamp": "ISO8601",
  "link": "secondary",
  "payload": {
    "phone_status": {
      "battery_level": 0.85,
      "network_type": "wifi",
      "current_tasks": 0,
      "storage_free_gb": 32.1
    }
  }
}
```

### 心跳参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 心跳间隔 | 15 秒 | PC 端发送心跳的间隔 |
| 心跳超时 | 5 秒 | 单次心跳等待响应的超时 |
| 离线判定 | 连续 3 次超时 | 连续 3 次心跳无响应标记副链路断开 |
| 恢复判定 | 1 次成功心跳 | 断开后收到 1 次成功心跳恢复 |

### 心跳检测流程

```
每 15 秒:
  PC 端 → 发送心跳 → 手机端
  手机端 → 回复心跳响应 → PC 端

  PC 端收到响应:
    → consecutive_failures = 0
    → 更新 phone_status
    → 如果之前副链路断开 → 标记恢复，输出链路指示器

  PC 端超时未收到响应:
    → consecutive_failures += 1
    → 如果 consecutive_failures >= 3:
        → 标记副链路断开
        → 输出链路断开指示器
        → 如果主链路也断开 → 标记设备完全失联
```

## 链路状态管理

### 链路状态枚举

| 状态 | 主链路 | 副链路 | 说明 |
|------|--------|--------|------|
| FULL | ✅ | ✅ | 双链路正常，最佳状态 |
| PRIMARY_ONLY | ✅ | ❌ | 仅主链路可用，副链路断开 |
| SECONDARY_ONLY | ❌ | ✅ | 仅副链路可用，主链路断开 |
| DEGRADED | ⚠️ | ⚠️ | 双链路都不稳定（高延迟） |
| OFFLINE | ❌ | ❌ | 完全失联 |

### 状态转换规则

```
FULL → PRIMARY_ONLY: 副链路连续3次心跳超时
FULL → SECONDARY_ONLY: 主链路 device_chat 调用失败
FULL → DEGRADED: 双链路延迟都 > 5s
PRIMARY_ONLY → FULL: 副链路恢复1次心跳
SECONDARY_ONLY → FULL: 主链路恢复1次成功调用
PRIMARY_ONLY → OFFLINE: 主链路也断开
SECONDARY_ONLY → OFFLINE: 副链路也断开
```

### 状态对路由决策的影响

| 链路状态 | 路由行为 |
|----------|----------|
| FULL | 正常路由，proximity 基于主链路延迟 |
| PRIMARY_ONLY | 正常路由，但记录副链路异常 |
| SECONDARY_ONLY | 降级路由，proximity × 0.5 |
| DEGRADED | 谨慎路由，仅处理紧急任务 |
| OFFLINE | 不可路由，触发 failover |

## 紧急通知通道

当主链路断开但副链路可用时，副链路可以传递紧急通知：

### 崩溃风险通知（最重要场景）

```
PC 端检测到崩溃风险
  → 主链路可能已不稳定
  → 通过副链路发送 "crash_risk_split" 通知
  → 手机端收到后接管任务调度
```

### 设备恢复通知

```
PC 端从崩溃中恢复
  → 重新建立副链路
  → 通过副链路发送 "recovery" 通知
  → 手机端收到后可以重新分发任务
```

### 状态同步通知

```
PC 端状态变化（如内存告警）
  → 通过副链路发送 "status_change" 通知
  → 手机端调整路由策略
```

## 副链路消息类型

| 消息类型 | 方向 | 说明 |
|----------|------|------|
| link_establish | PC → 手机 | 建立副链路握手 |
| link_ack | 手机 → PC | 握手确认 |
| heartbeat | PC → 手机 | 心跳请求 |
| heartbeat_ack | 手机 → PC | 心跳响应 |
| crash_risk_split | PC → 手机 | 崩溃风险拆分通知 |
| recovery | PC → 手机 | 设备恢复通知 |
| status_change | PC → 手机 | 状态变化通知 |
| link_terminate | 双向 | 断开副链路 |

## 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `dual_link_enabled` | true | 是否启用双链路 |
| `network_heartbeat_interval` | 15s | 副链路心跳间隔 |
| `network_heartbeat_timeout` | 5s | 心跳超时 |
| `network_offline_threshold` | 3 | 连续心跳失败触发断开 |
| `network_port_range` | 10000-10100 | 副链路端口范围 |
| `link_establish_timeout` | 10s | 握手超时 |

## 安全考虑

- 副链路仅在本地网络或已认证的设备间建立
- 心跳消息不包含敏感数据（仅状态信息）
- 副链路断开不影响主链路的安全性
- 副链路消息有设备 ID 验证，防止伪造

## 边界

- 副链路不替代主链路，仅作为补充
- 副链路不传输文件内容（仅传输控制消息和状态）
- 副链路断开不等于设备离线（主链路可能仍可用）
- 副链路的心跳不消耗用户可见资源（后台静默运行）
- 副链路端口仅在本地监听，不暴露到公网
